怎麼做 SPEC

          
SPEC 是合約：AI 照著做，你照著驗收。

        

        約 8 分
      


      

        

          
          
          
        

        

          

            
    
              
  1. 背景與目標 — 為什麼做、成功長怎樣
    2. 
              
  2. 使用者與場景 — 角色、頻率、裝置
    3. 
              
  3. 功能清單 — Must / Should / Could
    4. 
              
  4. 非功能 — 延遲、安全、語系、引用必填
    5. 
              
  5. 資料與知識 — 來源、更新節奏、權限
    6. 
              
  6. 介面與流程 — 對應流程圖節點
    7. 
              
  7. API / 整合 — 端點、錯誤碼、限流
    8. 
              
  8. 驗收與排除 — 做得到才算完、明確不做什麼
    9. 
            

          

          

            
先看「白話版」：這段 SPEC 是在跟 AI／工程師講清楚——使用者丟什麼進來、系統要吐什麼出去、什麼情況下不能臆測／亂答、多快要回、什麼事不做。

            

              

                
這功能叫什麼？

                
知識庫問答：使用者用平常說話的方式提問，系統先檢索知識庫相關段落，再請語言模型（LLM）依段落作答。

              

              

                
輸入（使用者給系統什麼）

                
一段自然語言問題，也就是一般人講話的句子，不是程式碼。

                
限制：最多約 500 字，避免一次貼整份報告把系統塞爆。

              

              

                
輸出（系統要交什麼作業）

                
    
                  
  • 答案：用人話回覆
    • 
                  
  • 引用 chunk id：標出「這句話是從知識庫哪一小段來的」（chunk＝切好的知識片段）
    • 
                  
  • 是否低信心：系統自評「我有沒有把握」；沒把握要坦白說
    • 
                

              

              

                
規則（什麼情況下不准亂答）

                
知識庫裡找不到夠用的依據時：不准臆測／亂答。改成反問使用者（請講清楚一點），或直接說不知道／拒答。

              

              

                
效能（要多快）

                
從按下送出到看到完整答案，大多數時候（約 95% 的請求）要在 8 秒內完成。寫這行是為了避免做出「正確但慢到不能用」的系統。

              

              

                
排除（明確說不做什麼）

                
    
                  
  • 不可僅提供最終法院判決：不能只丟一句判決結論；要附推論、依據與不確定的地方
    • 
                  
  • 不可只給法律建議卻沒有推論過程：可以給建議方向，但必須說清楚怎麼推導出來、依據哪段資料
    • 
                  
  • 不改寫原始政策文件：AI 可以引用、說明，但不能擅自改公司正式規定的原文
    • 
                

              

            

            

              對照：寫給 AI 的精簡原文
              
## 功能：知識庫問答
- 輸入：自然語言問題（≤ 500 字）
- 輸出：答案、引用 chunk id、是否低信心
- 規則：無足夠依據時不得臆測，改回問或拒答
- 效能：P95 端到端 < 8 秒
- 排除：不可僅提供最終法院判決／不可只給法律建議而無推論過程；不改寫原始政策文件

            

          

          

            
    
              
  • 給 10 題黃金問題，至少 8 題有正確引用
    • 
              
  • 刻意超範圍問題會被拒答或澄清
    • 
              
  • UI 可點開來源段落對照
    • 
              
  • 參數表與預設值寫在設定檔，可調
    •

        05
        

          
API 細節說明

          
接口地圖＋模型網址／驗證／API Key 怎麼貼、怎麼存——寫進 SPEC 才能接得上。

        

        約 8 分
      


      

        
你前面已經會寫「網頁要有問答、上傳知識庫」。但程式之間要怎麼呼叫？就像餐廳裡：

        
    
          
  • 網頁畫面＝客人（點餐）
    • 
          
  • API＝服務生（傳話窗口）
    • 
          
  • 後端／AI／知識庫＝廚房（真正做事）
    • 
        

        
所以 API 細節＝寫清楚：客人要點什麼、廚房會端什麼、點錯或廚房忙時怎麼回覆。寫給人看，也寫給 Codex 實作時照著做。

        
教學目的：學會在 SPEC／PROMPT 裡附上「接口地圖」＋「模型對接設定」（網址、模型名、驗證、Key 存放），避免 AI 只做出漂亮畫面卻接不上模型，或 Key 亂存造成外洩。

      


      

        
對接 AI 模型時，規格一定要寫的四件事

        
    
          
  1. Base URL／端點網址 — 例如 OpenAI 相容 https://api.openai.com/v1，或單位內部閘道。前端／後端打哪裡要寫死欄位，不要口頭講「接一下 API」。
    2. 
          
  2. 模型名稱 — 例如 gpt-4o、codex-…、或內部部署模型 id。頂欄「模型下拉」的選項要從設定來，可改。
    3. 
          
  3. 驗證機制 — 常見：HTTP Header Authorization: Bearer <API_KEY>；有的用 x-api-key。寫清「放哪個 header、有沒有額外 org／專案 id」。
    4. 
          
  4. API Key 載入與存放 — 誰輸入、存在哪、誰看得到、能不能進 Git。教學示範可用「設定頁貼上 → 本機 localStorage」；正式環境 Key 只放伺服器環境變數（.env），瀏覽器不要長期明文存正式金鑰。
    5. 
        

        
對接邏輯口訣：畫面按下提問 → 組請求（URL＋模型＋Header＋body）→ 呼叫 → 解析回覆／錯誤 → 更新 UI 狀態。這整段要寫進 SPEC，Codex 才知道設定頁與問答區怎麼串。

      


      
先點下面四張「模型對接」卡片，再點三張「業務窗口」卡片。


      

        

          
設定

          
Base URL

          
模型／閘道網址要貼哪、怎麼測通。

        

        

          
設定

          
模型名稱

          
下拉選什麼、請求 body 帶哪個欄位。

        

        

          
驗證

          
驗證機制

          
Bearer／x-api-key／額外標頭怎麼寫。

        

        

          
金鑰

          
API Key 存放

          
設定頁貼上、本機暫存 vs 伺服器 .env。

        

      


      
業務窗口：常見知識庫問答系統的三個呼叫口。


      

        

          
POST

          
/v1/chat/query

          
問答窗口：使用者提問 → 找回資料 → 生成答案。

        06
        

          
知識庫與 Markdown

          
好的知識庫像整理過的書櫃。切塊、下指令、驗收，都要能講清楚。

        

        約 10 分
      


      

        

          1
          
拆主題

          
一檔一事：請假、報銷、資安……

        

        

          2
          
寫結構

          
標題層級清楚，列表與表格利於切塊。

        

        

          3
          
加 metadata

          
版本、生效日、部門、權限標籤。

        

        

          4
          
切塊入庫

          
依標題切，再套 Chunk Size / Overlap。

        

      


      

        

          example.md
          
        

        
---
title: 請假規定
version: 2026.03
owner: HR
---

# 年假
- 到職滿一年：特休 7 天
- 申請需提前 3 個工作日

# 病假
- 需附證明（連續 2 天以上）
- 當年度上限依勞基法

        

          
HR · v2026.03

          
年假

          
    
            
  • 到職滿一年：特休 7 天
    • 
            
  • 申請需提前 3 個工作日
    • 
          

          
病假

          
    
            
  • 需附證明（連續 2 天以上）
    • 
            
  • 當年度上限依勞基法
    • 
          

        

      


      

        

          
          
          
          
        

        

          

            
優先依標題切，不要先依字數硬切。一塊＝一個可獨立引用的意思單位；Overlap 是保險，不是把主題混在一起的藉口。

            

              
              
            

            

              

                
chunk A# 年假

                
    
                  
  • 到職滿一年：特休 7 天
    • 
                  
  • 申請需提前 3 個工作日
    • 
                

              

              
──── 依 H1 切點 · overlap 只重疊邊界句 ────

              

                
chunk B# 病假

                
    
                  
  • 需附證明（連續 2 天以上）
    • 
                  
  • 當年度上限依勞基法
    • 
                

              

            

            
年假規則完整在 A、病假完整在 B。問「年假要提前幾天申請？」能整段引用。

            
    
              
  • 一檔一事；原則與例外必須同塊
    • 
              
  • 標題層級清楚：# 主題、## 小節、### 例外／注意
    • 
              
  • 用列表、表格，少寫長散文
    • 
              
  • Chunk Size 約 1500、Overlap 約 100 是起點；法規長文再視情況微調
    • 
            

          

          

            
不要只說「幫我整理知識庫」。把角色、切法、輸出欄位一次講完。點複製，貼進對話即可。

            

              

                
① 請 AI 整理成合格 Markdown

                
              

              
角色：你是知識庫工程師。
任務：把我貼上的資料整理成「可寫入向量索引、可被 Embedding 檢索」的 Markdown。
規則：
1. 一檔一事；檔名用主題，不要用「完整版」「彙整」
2. 標題：# 主題、## 小節、### 例外／注意
3. 原則與例外必須寫在同一節，不可拆檔
4. 開頭 YAML：title, version, owner, effective_date, tags
5. 用列表、表格，少寫長散文
6. 每節都要能單獨回答至少一個問題
輸出：完整 Markdown + 建議切塊邊界（標在 ##）+ 每塊能回答的範例問題

            

            

              

                
② 請 AI 審核切塊（不要硬切字數）

                
              

              
角色：你是 RAG 切塊審核員。
任務：檢查這份 Markdown 適不適合「依標題切 + chunk 1500 / overlap 100」。
請列出：
- 建議切點（標題）
- 哪裡會切太碎或切太雜
- 哪些原則／例外被拆開了
- 修正後的標題結構
禁止：直接依字數硬切、把例外和原則拆到不同塊。

            

          

          

            
對接成功不是「檔案有上傳」，而是黃金問題能找回正確段落，而且答得出引用。請 AI 當驗收官，不准只說「看起來可以」。

            
    
              
  1. 準備 8～10 題黃金問題（你已經知道標準答案）
    2. 
              
  2. 對每一題看：命中哪個 chunk、能不能引用原文
    3. 
              
  3. 失敗要分類，才能知道改 Markdown 還是改參數
    4. 
            

            

              
              
              
              
              
              
              
            

            

              
點上方失敗類型，看典型症狀與該改哪裡。

            

            

              

                
③ 請 AI 檢驗知識庫是否對接成功

                
              

              
角色：你是知識庫驗收官，不准只說「看起來可以」。
任務：用下列黃金問題檢驗知識庫是否對接成功。
對每一題輸出：
1. 應命中的檔名／標題
2. 實際檢索到什麼（若能讀檔就讀）
3. 能否引用原文
4. 判定：通過 / 失敗
5. 失敗類型：切太碎 | 切太雜 | 標題不清 | 缺 metadata | 主題混檔 | 文件過期 | 問題超範圍
最後給：通過率、不合格清單、我該改 Markdown 還是改參數（Chunk / Top-K / Rerank）。
通過標準：10 題至少 8 題命中正確段落且有引用。
黃金問題：
- （請填 8～10 題）

            

          

          

            
點選打勾，當現場驗收清單。全部打勾才算這份 Markdown「可以入庫」。

            
    
              
  • 一檔一事，沒有「彙整大全」
    • 
              
  • 標題即目錄：人看懂、機器切得動
    • 
              
  • 一塊能獨立引用，不需要前後文才懂
    • 
              
  • 原則與例外寫在同一節
    • 
              
  • YAML 有 title / version / owner / 生效日 / tags
    • 
              
  • 舊版有標註或已下架，不會跟新版搶命中
    • 
              
  • 黃金問題 ≥ 80% 能命中正確段落
    • 
              
  • 答案能指出 chunk／標題，人點得回原文
    • 
            

            
0 / 8 合格項

    實戰案例
    
          
    同一套方法，套在兩個真實產品上對照學習。
    
        
    
        約 8 分
      
    

      
    
        
        
      
    

      
      
    
        
    
          
    CASE · TP NOTE01
    
          
    TP AI NOTE · 移轉訂價專屬知識庫
    
          
    
            幫查核員／稅務同仁在查 OECD TPG、台灣 TP 查核準則、BAPA／MAP時，
            用自然語言問答拿到有知識庫引用的推論答案，並能存筆記、匯出、回寫知識庫。
          
    
          
    
            心智圖導覽
            本機 RAG
            法規 Markdown／PDF
            查核員 Prompt
            筆記匯出
          
    
          
    → 深入閱讀：AI NOTE 架構解說（引擎＋模組）
    
        
    

        
    
          
    
            
            
            
            
            
            
          
    
          
    
            
    
              
    
                
    
                  
    誰 × 情境 × 結果
    
                  
      
                    
    • 誰：TP／BAPA 查核與學習者
      • 
                    
    • 情境：法條多、跨 OECD／台灣／函令，難一次翻完
      • 
                    
    • 結果：可引用的答案 + 節點詳情 + 可存筆記
      • 
                  
    
                
    
                
    
                  
    MVP 邊界
    
                  
      
                    
    • 做：本機知識庫檢索 → 模型推論 → 引用
      • 
                    
    • 做：心智圖點選法規節點
      • 
                    
    • 不做：取代正式法律意見書
      • 
                    
    • 不做：無依據時硬答
      • 
                  
    
                
    
              
    
            
    
            
    
              
      
                
    1. 開始：使用者提問（例：BAPA 申請要注意什麼？）
      2. 
                
    2. 檢索：本機 TP 知識庫以向量索引（依意思找）／關鍵字命中段落
      3. 
                
    3. Rerank／篩選：依意圖（避風港、DEMPE、PE…）加權
      4. 
                
    4. 判斷：不足 → 澄清；足夠 → 生成
      5. 
                
    5. 生成：查核實務論述 +【參考依據】
      6.

    兩種做法，差在哪？
    
        
    
          
    
            
    ❌ 只做 Prompt + Markdown
    
            
      
              
    • 把整本規章貼進對話框，或靠模型「記憶」
      • 
              
    • 一次改 Prompt 就牽一髮動全身
      • 
              
    • 找不到段落時，模型容易幻覺／亂答
      • 
              
    • 無法穩定引用、無法量測「這次答得好不好」
      • 
            
    
          
    
          
    
            
    ✅ 引擎 + 模組（TP NOTE01 做法）
    
            
      
              
    • 知識先切塊入庫，問答時先檢索再生成（）
      • 
              
    • 檢索、重排、組裝、生成、後處理分開維護
      • 
              
    • 低信心走澄清／拒答，不硬掰
      • 
              
    • 輸出固定格式：推論、答案、實務重點、
      • 
            
    
          
    
        
    
        
    白話：Prompt 是「廚師守則」，但還要有食材庫（知識庫）、點菜系統（編排引擎）、品管（後處理），才像一間能穩定出菜的餐廳，而不是每次現場翻冰箱。

    Hook · MCP · Subagent · Workflow
    
          
    AI 不只會寫字。把它接上工具、門禁與分工，才叫工作流。
    
        
    
        約 8 分
      
    

      
    點卡片看白話比喻。四件事常常一起出現：知識用 Markdown，外部系統用
        ，
        自動檢查用 ，
        大任務用 ，
        整套串起來就是 
        （搭配  把做法寫成可重用手冊）。
      
    

      
    
        
        
        
        
      
    

      
    
        
    比喻：門口保全——Agent 要出門或進門前，先檢查證件。
    
        
    Hook（鉤子／事件攔截）
    
        
    Hook 是「某件事發生之前或之後，自動跑一段檢查或後續動作」。不是讓人每次盯著看，而是把規則寫進事件裡。
    
        
      
          
    • 改完檔自動格式化
      • 
          
    • 危險指令（刪檔、對外連網）先問人
      • 
          
    • 送出前提醒：不要貼金鑰、個資
      • 
          
    • Subagent 結束後，自動接下一棒
      • 
        
    
      
    

      
    
        
    什麼時候用哪個

    知識要被找到Markdown 切塊 + 黃金問題驗收

    做事前／事後自動檢查Hook
    
          
    大任務要分工或平行Subagent
    
          
    整套要可重複給同事用Workflow（SPEC ＋ Skill ＋ 上述工具）

    給 AI 看 · 對照說明
    
      
    人腦流程 → AI 步驟清單
    
      
    流程圖對人來說已經夠清楚；對 AI 要再拆成可執行的步驟與欄位，再寫進 SPEC／PROMPT。
    

      
    
        
    例如你腦中的流程可能是
    
        
    
          案件資料
          →
          判斷交易類型
          →
          找受測個體
          →
          功能風險分析
          →
          選擇利潤率指標
          →
          撰寫論述
          →
          人工確認
        
    
        
    這對人來說已經很清楚。
    
      
    

      
    
        
    但對 AI 來說，最好進一步寫成
    
        
    
          
    
            Step 1：取得案件基本資料
            
      
              
    • 公司名稱
      • 
              
    • 所在地
      • 
              
    • 關係企業
      • 
              
    • 交易類型
      • 
              
    • 交易金額
      • 
            
    
          
    
          
    
            Step 2：辨識受測個體
            
      
              
    • 分析交易雙方功能
      • 
              
    • 分析承擔風險
      • 
              
    • 判斷誰較適合成為受測個體
      • 
              
    • 輸出選擇理由
      • 
            
    
          
    
          
    
            Step 3：進行功能風險分析
            
      
              
    • 製造功能
      • 
              
    • 採購功能
      • 
              
    • 銷售功能
      • 
              
    • 研發功能
      • 
              
    • 市場風險
      • 
              
    • 存貨風險
      • 
              
    • 信用風險
      • 
            
    
          
    
          
    
            Step 4：選擇最適利潤率指標
            
      
              
    • 判斷交易性質
      • 
              
    • 比較適用的 PLI
      • 
              
    • 說明為何選擇該指標
      • 
            
    
          
    
          
    
            Step 5：產生報告文字
            
      
              
    • 依前述步驟產出可審閱的論述草稿
      • 
            
    
          
    
          
    
            Step 6：列出 AI 判斷依據及不確定事項
            
      
              
    • 標出引用／推論依據
      • 
              
    • 標出需人工確認的不確定點
      •
